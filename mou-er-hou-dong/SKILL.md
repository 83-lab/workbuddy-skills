# 谋而后动

## 核心理念

**重设计 · 重审核 · 轻实施**

80% 的时间花在想清楚，20% 的时间花在干清楚。一次想透，一次做对。

**核心原则：**
1. **目的导向** — 设计是为了实现目标，不为对比而对比，不为流程而流程
2. **实事求是** — 多少方案写多少，简单步骤直接过，不硬凑
3. **先理解再动手** — 每条需求写清目标/输入输出，不清楚先问，可做小示例确认
4. **需求清单驱动** — 需求清单是整个流程的"宪法"，所有设计/执行/自检/偏差/变更都对照它
5. **偏差有管理** — 执行出问题先评估影响范围，确定影响再解决，做完记录留经验
6. **变更有流程** — 任务进行中增改需求，先评估影响再决定是否执行，确保清单最新
7. **自审 + 熔断** — 执行前自审，执行后自检，3 次不过熔断通知
8. **经验可复用** — 完成即沉淀，形成追溯矩阵和经验库，越用越稳

## 上下文管理（全局）

**问题：** 复杂任务对话可能很长，上下文窗口容易爆，导致模型"中间迷失"。

**对策：定期状态确认 + 上下文压缩**

1. **阶段衔接时做状态确认**：切换阶段前，先确认当前已确认的内容，对齐认知
   ```
   "当前已确认的关键结论：
   1. 需求清单：[已确认需求摘要]
   2. 设计方案：[已确认方案摘要]
    
   现在进入下一阶段：[阶段名称]
   以上理解是否正确？"
   ```

2. **关键信息在提示词中重复**：切换阶段时，在开头总结已达成的结论
   - 把已确认的结论放在阶段开始时重申
   - 让对话上下文聚焦当前阶段的核心任务

3. **对话确实会爆时**：输出完整交接文件，另开任务执行（见阶段二）

4. **提审后无回复（晨哥自主审查模式）：**
   - 晨哥会自主安排时间审查，无需自动催促
   - 如果超过预期时间（如半天以上）未见反馈，可主动问候确认是否需要继续

## Temperature / Top-P 参数指南（全局参考）

**遵循「提示词工程专家」skill 的参数建议。关键原则：**
- **评估/设计类**（方案设计、偏差影响评估、变更评估）→ Temperature 可高一些（0.3~0.7），覆盖更全面
- **文件整理/代码类**（需求整理、代码执行、格式转换）→ Temperature 要低（0.1~0.2），确保精确

| 场景 | Temperature | Top-P | 策略说明 |
|------|-------------|-------|----------|
| 需求整理（阶段一） | 0.1 | 0.1 | 精确分类，不允许乱改 |
| 方案设计/评估（阶段二） | 0.3~0.5 | 0.4~0.5 | 适度多样性，覆盖全面 |
| 代码执行/文件操作（阶段三四） | 0.1 | 0.1~0.2 | 精确优先，不能出错 |
| 偏差影响评估（阶段四偏差管理） | 0.3~0.4 | 0.4 | 需要系统性地覆盖影响面 |
| 变更影响评估（阶段五） | 0.3~0.4 | 0.4 | 评估全面性与准确性平衡 |
| 追溯整理（阶段八） | 0.1 | 0.1 | 整理类任务必须精确 |
| 经验沉淀（阶段九） | 0.1~0.2 | 0.2 | 格式一致性优先 |

**公式：Temperature 越低 → 输出越确定；越高 → 输出越多样。**

如果任务结果有"标准答案"，Temperature 越低越好。如果结果是"需要提供选项或全面覆盖"的，适中的 Temperature 更有利。

> ⚠️ **提示**：此为设计参考。在实际 WorkBuddy 对话中，Temperature/Top-P 由平台模型自动控制，无法手动设定。

仅以下情况触发此流程：
- 晨哥明确说"这任务复杂，走谋而后动流程"
- 晨哥手动调用此 skill
- 任务明显涉及多文件修改、多需求、逻辑分支复杂

简单任务（改个变量、查个资料、跑个命令）直接执行，不走此流程。

## 完整 9 阶段流程

### 阶段一 · 理解任务（产出：需求清单 + 小示例确认）

**做什么：**
1. 逐条理解晨哥交代的每个需求
2. **有不清楚的地方先问，不猜**
3. **可以做小示例让晨哥确认**：如果对某个需求的理解不太确定，直接做个简短的示例（比如一条数据样例、一段伪代码、一个输出格式样本）给晨哥看
   - 晨哥看完会说"对，就是这样"或者"不对，应该是这样"
   - 如果示例不对，晨哥会按他的意思修改示例，你就明白了
4. **调用 提示词工程专家 + json-prompting skill 生成需求清单双格式**

**需求模板：**
- **目标** — 一句话说清这个需求要达成什么（晨哥必给）
- **输入/输出** — 给什么、出什么（晨哥必给）
- **依赖/假设** — 有什么前提条件（我不清楚才问，不预设）
- **疑点** — 我有疑问的地方（我不清楚才问，不预设）

**不需要模板的每一个字段都填。** 晨哥只给目标和输入输出，其他字段只有我觉得不清楚的时候才写，不要预设晨哥有疑问。

**产出：需求清单（双格式）**

格式 A — **自然语言版（晨哥看）**
```
需求 1：[自然语言描述]
需求 2：[自然语言描述]
...
```

格式 B — **JSON 提示词版（AI 执行用）**
调用 `json-prompting` skill 将自然语言需求清单转换为结构化的 JSON 提示词，包含：
- 角色设定（参考「提示词工程专家」skill 案例）
- 输入/输出 schema
- 约束条件
- 输出格式要求
- 自洽性要求（多步校准，参考「提示词工程专家」skill 2.4）

**目的**：晨哥审自然语言版确保需求没错，AI 执行时用 JSON 版减少幻觉。

**梳理完成后，提交晨哥审核需求清单。**

**⚠️ 需求清单是整个流程的"宪法"** — 后续所有设计、执行、自检、偏差管理、变更管理都以此为准。

### 阶段二 · 设计方案（产出：完整方案）

**理清思路：**
- 重新梳理任务的本质目标
- 参考「提示词工程专家」skill 的设计思路（如 Role Prompting、Few-shot、CoT、ToT、ReAct 等）：
  - 使用角色设定（Role Prompting）— 2.1
  - 使用 Few-shot 示例明确输出格式 — 2.2
  - 复杂推理使用思维链（CoT）— 2.3
  - 多路径探索使用思维树（ToT）— 2.6
  - 需要外部信息用 ReAct — 2.5
- 评估对话上下文长度
  - 如果本对话内完成设计+执行会导致对话过长，在方案确认后，**输出完整的设计交接文件**，建议晨哥另开新任务执行
  - 交接文件要写出完整的交代内容（所有步骤 + 实现细节 + 注意事项），确保换任务后没有遗漏

**设计方案（实事求是，不硬凑）：**
- 有多少方案写多少，一个就一个，两个就两个
- 简单步骤直接写，不需要对比
- 每个方案写清：
  - 核心思路
  - 优缺点
  - 推荐哪个 + 为什么

**方案整体展示（不是逐条展示）：**
- **完整步骤清单**，每步按四要素：
  - **做什么**：这一步具体算什么/写什么/干什么
  - **怎么做**：用什么工具、技术、方法来实现
  - **注意事项**：边界情况、易错点、风险提示
  - **为什么要做**：这一步在整个方案中的角色
- 步骤粒度根据需求复杂程度调整
  - 简单需求一步到位
  - 复杂需求拆细，以便出问题时精准定位到哪步出错
- **影响范围评估**：会改动哪些文件 + 风险等级（展示给晨哥看）

**自审（不满足不提审，完整清单见检查清单章节）：**
直接对照「设计方案自审清单」逐条检查。
如果自审发现问题 → 修改 → 再审
🔴 **满 3 次仍不过 → 熔断，通知晨哥：** 卡在哪一步 + 尝试了什么 + 为什么没过去

**审核通过后 → 提交晨哥批整方案：**
- 晨哥看整个方案
- **单步有问题** → 只改单步，其他不动
- **整个方案有问题** → 全回溯，重新设计

### 阶段三 · 设计执行方案（产出：具体代码/脚本/工具调用）

**做什么：**
基于已确认的设计方案，设计具体的执行内容：
- 代码结构、脚本逻辑
- 工具调用方案
- 文件变更清单
- 具体的实现细节

**影响范围评估（展示给晨哥）：**
| 文件路径 | 操作类型 | 风险等级 | 说明 |
|----------|---------|---------|------|
| xxx.py | 修改 | 低 | 新增功能 |
| xxx.json | 修改 | 中 | 结构变化 |

**影响范围评估要展示给晨哥看。**

**执行前备份：**
- 对将要修改的文件进行备份
- 备份位置：目标文件所在目录下新建 `谋而后动/` 文件夹
- 命名规则：`谋而后动/文件名.备份.YYYY-MM-DD`
- 如果备份恢复失败 → 告知晨哥备份文件的具体路径，由晨哥手动恢复

**自审（简化版，完整清单见检查清单章节）：**
直接对照「执行方案自审清单」逐条检查。
- 发现问题 → 修改 → 再审
🔴 **满 3 次仍不过 → 熔断，通知晨哥**

---

### 阶段四 · 执行 + 偏差管理（产出：执行结果）

**做什么：**
按确认的方案执行。

**执行期间出问题怎么办（偏差管理）：**

当执行过程中遇到预期之外的错误或异常时：

**① 发现问题 → 暂停**
- 立即暂停当前操作
- 记录问题现象

**② 评估影响范围**
判断这个问题：
- **影响大不大？** — 是否影响其他步骤的执行？是否影响已完成的产出？
- **影响哪些内容？** — 对需求清单中的哪些需求有影响？对其他步骤有什么连锁反应？
- **严重等级** — 轻微（可原地解决）/ 中等（需调整后续步骤）/ 严重（需重新设计方案）

**③ 确定解决方案**
- **影响小** → 在原地解决，修复后继续，并记录解决方式
- **影响中等** → 调整后续步骤方案，通知晨哥变更情况
- **影响严重** → 熔断通知晨哥，讨论是否需要回溯设计

**④ 执行解决**
- 按确定的方案解决问题
- 修改后重新验证受影响的内容
- 更新备份

**⑤ 记录经验（调用 Self-Improving + Proactive Agent skill）**
- 记录：什么问题 → 怎么评估的 → 什么方案解决的
- 调用 Self-Improving + Proactive Agent skill 写入记忆
- 目的是：越用越好，下次遇到类似问题不用重新想

**偏差管理的目标：** 发现问题后不盲目修复，先评估影响再决定怎么处理，减少问题对任务的冲击范围。做完后留下记录，积累经验。

**执行后自检（简化版，完整清单见检查清单章节）：**
直接对照「执行后自检清单」逐条检查。
- 发现问题 → 修改 → 再自检
🔴 **满 3 次仍不过 → 熔断，通知晨哥**

### 阶段五 · 变更管理（任何时间触发）

**触发条件：** 需求清单已确认后，晨哥提出新需求或变更已有需求。

**流程：**

**① 接收变更请求**
- 记录晨哥提出的变更内容

**② 评估影响**
评估此变更对：
- **设计方案**的影响 — 是否需要重新设计？改动多大？
- **执行方案**的影响 — 代码/脚本需要改多少？哪些已完成的产出需要调整？
- **已执行内容**的影响 — 是否有已完成的步骤被此变更推翻？

**③ 与晨哥沟通**
- **影响小** → 直接说"这个变更影响不大，可以执行，更新需求清单后继续"
- **影响大** → 说清楚影响范围和建议，让晨哥决定："这个变更会波及 xxx，需要重新设计部分方案，是否执行？"
  - 晨哥说执行 → 更新需求清单，回到相应阶段
  - 晨哥说不执行 → 保持原清单，继续

**④ 更新需求清单**
- 如果要执行，先更新需求清单
- 确保需求清单始终是**最新版本**（增加的用新编号、修改的标注版本）
- 所有后续阶段以新清单为准

**变更管理的目的：** 不是阻止变更，而是让每个变更的影响被充分评估后再执行，避免"加个小功能结果全崩了"的情况。

### 阶段七 · 收尾

**执行成功后：**
1. **问晨哥："还有没有问题？"**
   - 有 → 根据反馈继续修改
   - 没有 → 继续
2. **问晨哥："要不要做成 skill 方便以后复用这个工作流？"**
   - 要 → 创建或更新 skill
   - 不要 → 继续

### 阶段八 · 追溯统计（产出：追溯矩阵）

**做什么：**
建立**追溯矩阵**，将整个任务过程中关键链路串联起来。

**追溯矩阵模板：**

| 需求编号 | 需求描述 | 设计方案 | 执行方案 | 使用工具/脚本 | 产出文件 | 偏差记录 | 经验备注 |
|----------|---------|----------|----------|-------------|---------|---------|---------|
| REQ-01 | xxx | 方法A | script_A.py | Python/pandas | result_A.csv | — | 可复用 |
| REQ-02 | xxx | 方法B | tool_B.sh | shell/sed | config_B.json | 见偏差#1 | 需注意边界 |

**目的：**
- 任务出问题可以快速定位到是哪个需求哪个步骤出的问题
- 将来类似任务可以一键参考：这个需求上一次是怎么做的
- 晨哥的工作主要是精确性工作，不是创意性工作，所以可追溯、可复现是核心

### 阶段九 · 经验沉淀（产出：经验库）

**做什么：**
建立**个人通用经验库**，跟项目解耦，换项目不丢。达到"越用越稳"的长期目标。

**经验库位置：** `D:\经验库\`（独立于 C 盘，不依赖任何项目工作空间）

**按任务类型分类目录：**

```
~/.workbuddy/经验库/
├── README.md                    ← 根目录说明：库的结构和使用方式
│
├── 01-项目文件编制/             ← 基于旧项目文件改新项目
│   ├── scripts/                 ← 可复用脚本（什么用途、输入输出格式）
│   ├── prompts/                 ← 对应提示词备份（怎么生成这个脚本的）
│   ├── templates/               ← 执行方案模板/文档模板
│   ├── examples/                ← 成功产出示例（输入+输出对照）
│   └── README.md                ← 该类型说明、使用频率、注意事项
│
├── 02-文档翻译/                 ← 中文→中英双语翻译
│   └── (同上结构)
│
├── 03-评估文件编写/             ← 风险评估等评估类文件
│   └── (同上结构)
│
├── 04-业主反馈修改/             ← 按业主意见修改已写文件
│   └── (同上结构)
│
├── 05-验证附件整理/             ← 原始资料→测试清单 / 截图→Word附件
│   └── (同上结构)
│
└── 06-追溯矩阵/                 ← URS→风评→DQ→IQ/OQ/PQ整体追溯
    └── (同上结构)
```

**每种任务类型文件夹内统一结构：**

| 子目录 | 存放内容 | 目的 |
|--------|---------|------|
| `scripts/` | 可复用脚本（Python/bash等） | 下次直接用，标注用途+输入+输出+注意事项 |
| `prompts/` | 生成脚本时的提示词备份 | 还原"当时怎么想到这个方案的"，下次调整也方便 |
| `templates/` | 执行方案模板、文档模板 | 类似需求直接套框架 |
| `examples/` | 成功产出示例（input+output对照） | 下次对标这个标准 |
| `README.md` | 该类型的说明和使用方式 | 快速上手 |

**⏫ 自动升格规则：**

- **复用 1-2 次** → 在经验库里引用、记录
- **复用 ≥ 3 次** → 自动升格为 WorkBuddy skill，下次 `/技能名` 直接调
  - 升格时：将 `scripts/` + `prompts/` + `templates/` 整合为 skill
  - 删除经验库中的原始记录，避免冗余
  - 在 `经验库/README.md` 中记录 skill 名称和路径

**偏差经验通过 Self-Improving + Proactive Agent skill 持续积累**，不在经验库中重复存储。

**长期目标：**
完成任务只是工作之一——
- 储备知识，让每个任务都在积累
- 逐步构建自动化工作流，减少重复劳动
- 保证产出稳定，因为精确性是晨哥工作的核心，不是创意工作

## 流程图

```
阶段一 · 理解任务
└─ 晨哥交代需求 → 逐条整理 → 有疑问做小示例确认 → 双格式需求清单（自然语言+JSON提示词）
   └─ 产出：需求清单（晨哥审核确认）
       │
阶段二 · 设计方案
└─ 理清思路 → 设计方案（不硬凑）→ 自审对照需求清单
   └─ 过关 → 晨哥批整方案
      ↻ 3次不过 → 熔断
       │
阶段三 · 设计执行方案
└─ 具体代码/脚本 → 影响范围评估 → 执行前备份
   └─ 自审：需求清单 + 代码专业审查 → 过关 → 提交晨哥
      │                                    ↻ 3次不过 → 熔断
       │
阶段四 · 执行 + 偏差管理
└─ 执行 → [出问题→评估影响→解决→记录经验] → 自检对照需求清单
   └─ 过关 → 下一步
      ↻ 3次不过 → 熔断
       │
   ←—— 阶段五 · 变更管理（随时触发，非线性）——→
   │     └─ 接收变更 → 评估影响 → 沟通晨哥 → 更新需求清单
   │
阶段六 · 提交
└─ 已实现 / 未实现 → 晨哥决定：继续搞 vs 自己改
       │
阶段七 · 收尾
└─ 还有问题？→ 要做 skill？
       │
阶段八 · 追溯统计
└─ 建立追溯矩阵（需求→方案→工具→产出→偏差）
       │
阶段九 · 经验沉淀
└─ 整理可复用脚本/方案模板/产出示例/偏差经验 → 存入经验库
```

---

## 熔断机制（全局适用）

任何自审/自检循环：
- 1 次不过 → 修改
- 2 次不过 → 重新审视方案 → 修改
- **3 次不过 → 立即熔断，通知晨哥**
  - 通知内容：卡在哪一步 + 尝试了什么方案 + 为什么始终过不去
  - 晨哥决策后继续

## 检查清单（自审/自检用）

### 设计方案自审清单
- [ ] 每条需求都有对应的设计路径
- [ ] 选用的方案最简单有效（不做过度的设计）
- [ ] 步骤完整无遗漏
- [ ] 影响范围已评估（文件清单 + 风险等级）
- [ ] 提示词设计参考了「提示词工程专家」skill 思路（角色/Few-shot/CoT/ToT）

### 执行方案自审清单
- [ ] 每条需求都能通过此方案实现
- [ ] 代码/脚本没有语法错误
- [ ] 代码/脚本没有逻辑 BUG
- [ ] 边界情况已处理
- [ ] 备份已执行（目标文件同级 → 谋而后动/文件名.备份.日期）
- [ ] 偏差可能路径已考虑（什么场景下可能出错，如何应对）

### 执行后自检清单
- [ ] 每条需求已实现
- [ ] 实现结果正确、格式符合要求
- [ ] 功能完整可用
- [ ] 无偏差发生，或有偏差且已记录

### 追溯/经验清单
- [ ] 追溯矩阵已建立
- [ ] 可复用脚本已整理
- [ ] 偏差经验已记录（调用 Self-Improving skill）
- [ ] 产出示例已保留
